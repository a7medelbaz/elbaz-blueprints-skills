# DocsGuard adaptation

Before delivering technical learning Markdown, treat every factual statement as checkable. Verify versions, support status, compatibility, commands, paths, configuration keys, APIs, and course prerequisites against current authoritative sources available in the session.

For code samples, verify imports, signatures, language/environment labels, prerequisites, clean-machine assumptions, secrets hygiene, and a realistic failure path. Name the relevant version for version-dependent claims. Remove unsupported performance, scale, compatibility, or “production-ready” claims.

Link upstream documentation instead of paraphrasing changing manuals. Check headings, navigation, internal links, and anchors; remove TODOs and filler. Mark claims that cannot be verified as limitations or assumptions rather than fabricating certainty.

Final self-check:

1. Are all technical names, commands, paths, APIs, links, and numbers sourced or explicitly qualified?
2. Would each sample work in its stated environment?
3. Are facts separated from recommendations and learner decisions?
4. Are stale or versionless claims removed?
5. Do all internal links resolve and does navigation match the files?
