# Adaptive discovery and critique

Use a staged, adaptive interview. Begin with a set of three to five related high-impact questions; follow with another set only when an answer is missing, uncertain, or changes the plan. The learner must be able to receive a useful plan from guided self-assessment alone.

## Universal discovery

Establish these areas before planning:

1. **Real outcome:** the target role, real task, deliverable, domain, or deadline outcome.
2. **Current ability:** what the learner has built alone, can use, or can explain, including transferable programming languages, tools, and projects.
3. **Self-assessment:** for each capability that materially affects the plan, collect a confidence level (`new`, `can follow examples`, `can build alone`, or `can explain and debug`), where it was used, and uncertainty or desired refresh level.
4. **Time and context:** realistic weekly capacity, deadline, location/language, budget, device/environment, and work or study constraints.
5. **Target proof:** the portfolio project, work task, interview, certification, or personal outcome that will show readiness.

Ask subject-specific follow-ups only after the universal set. For example, a Python path may assess functions, files, errors, packages, APIs, SQL, Git, and testing. An Odoo path may additionally assess PostgreSQL, Linux, HTTP, business workflows, and the intended Odoo role.

## Placement and diagnostics

Classify each competency as `demonstrated`, `learner-reported`, `verify or refresh`, `required now`, `required later`, `optional`, or `out of scope`.

Treat self-assessment as a valid provisional placement and label it `learner-reported`; do not require a repository, code sample, quiz, or diagnostic before creating a plan. Use a micro-diagnostic only when a consequential placement decision remains unclear and a short, work-matched task would resolve it more efficiently than review. A diagnostic must be optional and lead to one concrete adjustment: reuse, refresh, begin a prerequisite, or advance.

## Decision checkpoint

Before research-heavy design, summarize the real outcome, baseline, constraints, target proof, material assumptions, unresolved choices, recommended scope, and the evidence the learner will produce.

Before creating any plan, establish the real outcome, learner baseline, time capacity, constraints, and target proof. A standard or large roadmap additionally needs the target role or work domain and intended technology scope. When required information is unavailable, state the assumption and create a provisional plan with a checkpoint that validates it.

Stop discovery when every unanswered question would leave scope, sequence, depth, pace, resources, and evidence unchanged. Do not collect background details only because they are interesting.

## Useful challenges

- Flutter experience may transfer programming and Git habits, but it does not prove Python, HTTP, SQL, Linux, or backend competence. Reuse only what evidence supports and verify the rest.
- “Learn all Odoo modules” is not an actionable target. Narrow by role, business domain, and target workflows.
- “Finish in three months” is not a plan until weekly hours, baseline, and a realistic capability milestone are known.

Critiques should name the learner's choice, concrete risk, evidence or evidence gap, realistic alternative, recommendation, and any decision required.
